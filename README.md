# kaspi-feed

Сервис отдаёт два прайс-листа для Kaspi по постоянным ссылкам.

| Ссылка | Магазин | Что внутри |
|---|---|---|
| `/centersna.xml` | merchantid `Centersna` | матрасы + архив кабинета, склад `Centersna_PP1`, Алматы |
| `/matras.xml` | merchantid `30378397` | всё кроме матрасов, склады и города как в фиде 1С |
| `/health` | — | JSON: когда собрано, сколько офферов, была ли ошибка |
| `/` | — | то же на человеческом языке |

Остатки берутся из фида 1С, цены — из закрытой Google-таблицы (или из CSV). Файл, который забирает
Kaspi, — снимок целиком, а не дельта: в нём всегда все офферы магазина,
снятые с продажи идут как `available="no"` + `stockCount="0"`.

## Запуск

```bash
node src/server.mjs
```

Разовая сборка в файлы, без сервиса:

```bash
node scripts/build-once.mjs out
```

## Архитектура публикации

```
Google-таблица (закрытая, шаринг сервисному аккаунту на чтение)
        │  Sheets API, ключ в секрете
        ▼
приватный репозиторий: код + расписание раз в 30 мин
        │  push токеном из секрета
        ▼
публичный репозиторий: только centersna.xml и matras.xml + Pages
        │
        ▼
      Kaspi
```

На публичной стороне нет ни кода, ни воркфлоу, ни секретов — красть нечего.
Оба секрета живут в приватном репозитории:

| Секрет | Что это |
|---|---|
| `GOOGLE_SERVICE_ACCOUNT_JSON` | JSON-ключ сервисного аккаунта Google |
| `PRICES_SHEET_ID` | id таблицы с ценами |
| `PAGES_DEPLOY_TOKEN` | fine-grained токен, только публичный репо, `contents: write` |

Переменные (не секреты): `PAGES_REPO` (`R1kse/kaspi-xml`), `SOURCE_XML_URL`, `PRICES_SHEET_RANGE`,
`CENTERSNA_SOURCE_STORES`, `STOCK_CAP`.

Себестоимость может спокойно лежать в той же таблице: в XML она не попадает
по построению, а таблица закрыта аутентификацией, а не «секретной ссылкой».

## Настройки

Все через переменные окружения, см. `.env.example`. Главные:

- `SOURCE_XML_URL` — фид 1С с остатками.
- `PRICES_SHEET_ID` + `GOOGLE_SERVICE_ACCOUNT_JSON` — закрытая Google-таблица.
  Заданы обе — цены берутся оттуда. Ключ принимается как сырой JSON и как base64.
- `PRICES_CSV_URL` — запасной путь, если Sheets не настроен: URL или локальный
  файл (по умолчанию `data/prices.csv`).
- `REBUILD_MINUTES` — период пересборки, по умолчанию 15.
- `CENTERSNA_SOURCE_STORES` — склад 1С, с которого Centersna берёт остаток.
  Сейчас `PP2`; уточнить, какой склад 1С физически стоит на Москвина 23.
- `STOCK_CAP` — потолок остатка в выгрузке, `0` = не ограничивать.

### Города и склады Centersna

В кабинете заведены `PP1`–`PP10`, включён только `PP1` (Алматы, Москвина 23),
остальные отключены. Поэтому в файле ровно один склад и один город —
специально, чтобы обкатать на Алматы. Города добавляются по одному:
в `CENTERSNA_STORE`/`CENTERSNA_CITIES` дописывается склад и его город,
и для него нужен свой склад-источник в `CENTERSNA_SOURCE_STORES` —
иначе остаток приедет алматинский, а товар лежит в другом городе.

## Таблица цен

Колонки ищутся по заголовку, порядок не важен:

- `sku` — артикул 1С;
- любая колонка со словом `kaspi` — цена;
- `Продавать` — `нет` снимает товар с продажи;
- `Магазин` — необязательно, перебивает разделение по названию;
- `Артикул Centersna` — необязательно, свой артикул для второго кабинета.

Если строки в таблице нет, цена остаётся такой, как в фиде 1С.

## Архив Centersna

`data/archive-centersna.xml` — выгрузка снятых с продажи товаров из кабинета
Centersna. Их нет в фиде 1С, но цену в кабинете держать надо, поэтому они
дописываются в конец `centersna.xml`:

- статус остаётся `available="no"`, `stockCount="0"` — обратно в продажу
  архив не поднимаем;
- цена берётся из таблицы по названию+размеру, если строка нашлась,
  иначе остаётся та, что была в кабинете;
- склад и город те же, что у живых офферов: `Centersna_PP1`, Алматы.
  В самой выгрузке архива торчат склады `PP12`, `PP17`, `PP24`, `PP27`,
  которых в кабинете уже нет, и 14 городов — всё это отбрасывается;
- офферы без названия и с ценой 0 не публикуются — Kaspi их не примет.

Тот же архив служит мостиком артикулов: у части живых матрасов артикул 1С
не совпадает с артикулом Centersna, и он подставляется по названию.
Название, встречающееся у двух разных артикулов, пропускается — не угадываем.

Файл обновляется руками: заново выгрузить архив из кабинета и закоммитить.

## Что сервис чинит в фиде 1С

- Кириллические `РР70` → латинские `PP70` (иначе Kaspi не знает такой склад).
- Дубли одного склада в оффере схлопываются по максимуму, а не по последнему.
- Дробные остатки → целые.
- `date="string"` → реальная дата в формате Kaspi по времени Алматы.

Чего сервис починить не может: в фиде остатки клонированы между складами
(девять складов показывают одни и те же 161 позицию). Это правится в 1С.

## Устойчивость

В памяти держится последняя **успешная** сборка. Если очередная пересборка
упала — сервис продолжает отдавать её же, а не пустой файл: пустой ответ снял
бы с продажи весь ассортимент. Сборка с нулём офферов тоже не принимается.

## Деплой

Docker-образ или Fly.io (`fly.toml` в репозитории). Машина не должна
засыпать: Kaspi ходит по ссылке раз в час, холодный старт отдаст 503.

## Безопасность

В репозиторий, XML и логи не попадают: пароли и куки Kaspi, токены, ключи,
данные покупателей, себестоимость и «Цена 1С». Публичный XML содержит только
артикул, название, бренд, остаток и цену продажи. Сервис никуда не логинится
под аккаунтом Kaspi.
